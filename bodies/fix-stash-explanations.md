## Summary

**The problem.** Git refuses `stash apply` / `stash pop` when files the stash touches have
uncommitted edits. Very often those edits *are* the stash: a pull with autostash (or a
manual apply that was never followed by a drop) leaves the changes in the working tree
and the stash still in the list. Applying it from Gitcito then fails with a toast that
opens on `On branch main / Your branch is up to date with 'origin/main'` (the `git status`
that `stash apply` prints first), wrapped in `Error invoking remote method 'git': Error:`.
The actual verdict sits several lines down, and nothing tells the user that there is
nothing left to apply. Anyone who pulls with local changes or keeps stashes around hits
this sooner or later.

A second, nastier case: with a `-u` stash, git reports both the tracked-file refusal and
"could not restore untracked files from stash". The app matched the untracked message
and offered *Overwrite & apply*, which deletes the stash's untracked files and retries,
only for the retry to fail again on the tracked files.

**What changes.**

- New read-only `gitService.stashAlreadyApplied(repoPath, index)` (in `READ_METHODS`,
  so it takes the shared lock). It diffs the stash's tracked files against the working
  tree and compares blob hashes of its untracked part (`stash^3`, only for `-u`) with
  the files on disk. True only when the working tree already holds exactly what the stash
  would restore.
- When an apply/pop fails with "Your local changes to the following files would be
  overwritten", the store asks that question:
  - already applied: a confirm, *This stash is already applied*, offering *Drop stash*.
    The changes stay in the working directory.
  - otherwise: an error toast naming the files in the way (up to three, then `…`):
    "Can't apply the stash: uncommitted changes in alpha.txt, beta.txt would be
    overwritten. Commit or stash them first."
- This check runs **before** the untracked-overwrite offer, so the overwrite is only
  proposed when untracked files are the only thing in the way.
- Every git error toast from `run()` now goes through `readableGitError`, which strips the
  IPC / simple-git wrapper and leads with git's own `error:` / `fatal:` line. The rest of
  git's output stays below it, so "Show more" still reaches it.
  This complements #51, which already drops the same wrapper from the title of a
  *Report issue* link (`issueTitle` in `lib/issueReport.ts`); that only touches the issue
  title, not the toast itself, so the two compose: the toast reads cleanly, and the
  reported issue body still carries the message as shown.
- New pure module `src/renderer/src/lib/gitErrors.ts` (`readableGitError`,
  `overwrittenLocalChanges`, `summarizePaths`).
- Four new keys (`stash.alreadyApplied.title/.message/.ok`, `stash.blockedByChanges`),
  translated in all 16 locales with identical placeholders.
- Handbook: `docs/help/stashes.md`, section *When a stash will not apply*, with a
  screenshot generated by a new `stash-already-applied` entry in `shots.config.mjs`.

**Benefits.** A failure that looked like a conflict becomes a one-click cleanup; a real
blocker names the files to deal with; and generic git errors open on the line that
explains them instead of on `git status` noise. The overwrite flow no longer deletes
untracked files for a retry that cannot succeed.

**Limits.** The check compares contents, so it cannot tell an applied stash apart from
edits that happen to be retyped identically. Either way, applying would change nothing, so
dropping is still safe. Dropping a stash has no undo (same as the existing *Drop stash*);
the confirm says the changes stay in the working directory. It only recognises git's
English "would be overwritten" message, like the existing untracked-collision check.

**Tests.**

- `test/pureLogic.test.ts`, `readableGitError`: wrapper stripped, verdict first with the
  status kept below, messages that already open on their verdict left alone, blocking
  files parsed, non-matching errors give `null`, path summarising.
- `test/gitOps.test.ts`, `stash already applied` (real git on a cloned `stash-picking`
  fixture): false on a clean tree, true after `stash apply` without a drop, false
  again after an edit; the untracked part of a `-u` stash is checked too; a real re-apply
  error yields the blocking files and `readableGitError` leads with "would be overwritten".

**How to test by hand.**

1. Open `examples/playground/stash-picking` (it has one `-u` stash).
2. In a terminal: `git -C examples/playground/stash-picking stash apply` (leave the stash).
3. In Gitcito, apply or pop the stash: *This stash is already applied* appears. *Drop
   stash* removes it from the list; the working tree is unchanged.
4. Reset (`npm run playground:rebuild`), apply again from the terminal, then edit
   `alpha.txt`, and apply from Gitcito: the error toast names `alpha.txt, beta.txt,
   src/gamma.txt` instead of showing `git status`.
5. Any other failing git action (e.g. checkout with conflicting local edits) shows a
   toast that opens on git's `error:` line.
